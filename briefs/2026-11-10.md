## 12. Deep dive: Qubole's trusted AWS account used against its customers (Wiz, 9 Nov) [NEW]

**Why it matters:** consultancies grant analytics and data-platform vendors cross-account IAM roles into their own and engagement AWS accounts. This case shows what happens when the vendor's side of that trust is compromised: valid External IDs, successful AssumeRole, and a path from cloud secrets into Entra ID and Okta.

### Sources
- https://www.wiz.io/blog/qubole-cross-account-access-abused-in-the-wild (Zack Morrow, Sean Johnstone, Benjamin Read; 9 Nov)
- https://thehackernews.com/2026/11/hackers-exploit-quboles-trusted-aws.html

### Attribution and confidence
- **Unattributed**; Wiz describes it as opportunistic; THN says targeting does not match typical state-backed groups. Sentra spotted it first in its customers' environments. How Qubole's credentials were obtained is not disclosed. No Qubole or Idera statement at time of reporting.

### Victims
- "Multiple" Qubole customer AWS environments; no count or sectors. Several lacked S3 data events and could not tell which objects were read.

### Timeline (Wiz)
- 8–11 Oct: separate activity using customer-owned keys believed created for Qubole integrations (all tested within an hour on 8 Oct); not linked to the role abuse.
- 14 Oct: first AssumeRole abuse (45.83.220[.]211). 15 Oct: most activity moves to 57.129.54[.]120 (OVH). 18 Oct: second IAM user; second Mullvad IP. 25 Oct: 89.37.63[.]175. 26 Oct: last activity from the primary IP. 9 Nov: disclosure.

### Initial access
- IAM credentials in Qubole's platform account **805246085872** used for sts:AssumeRole into customer roles that trust it, every call with a valid External ID. Wiz stresses External IDs are not secrets. Most abused roles were unused but still trusted Qubole.

### Behaviour and tooling
- Session names `quiam-*` (e.g. quiam-enum, quiam-scope-full). User agents: Boto3 1.37.9 (Debian, Python 3.13.5), aws-cli 2.37.12, Boto3 1.43.108 (aarch64), Boto3 1.43.113, TruffleHog.
- Discovery: ListBuckets, ListObjects, GetDatabases, ListTables, DescribeClusters, DescribeInstances, DescribeImages, DescribeSecurityGroups, DescribeVpcs, DescribeDBInstances, DescribeDBSnapshots, ListRoles, ListKeys, ListAliases, DescribeKey, GetKeyPolicy.
- Credential harvesting: Lambda GetFunctionConfiguration (env vars), Secrets Manager ListSecrets/GetSecretValue, SSM DescribeParameters/GetParameter. Validation with TruffleHog: GetCallerIdentity, Entra ID service-principal sign-ins, Okta OAuth token requests.
- Exfiltration: ListBuckets/ListObjects/HeadObject/GetObject, sometimes whole buckets.
- Staged but not seen deployed: `sso_agent.iso`, a bootable Linux image that uploads system info to 57.129.54[.]120, polls TCP 23458 for scripts, reboots after 90 minutes.

### Hunting (Wiz; CloudTrail from 1 Oct)
1. AssumeRole where userIdentity.accountId = 805246085872 and sourceIPAddress is not AWS.
2. Any activity by the principal IDs above (the second only from non-AWS IPs), or from the listed IPs.
3. GetCallerIdentity with a TruffleHog user agent; IdP (Entra, Okta) sign-ins with TruffleHog user agent.
4. Role session names `quiam-*`.
5. For each suspicious session, review Secrets Manager, SSM, Lambda and S3 actions; management events alone do not show S3 objects read.
- Analyst-added (not Wiz): alert on any vendor-account AssumeRole from VPN or hosting-provider ASNs, for every vendor, not just Qubole.

### Response and hardening (Wiz)
- Rotate every secret, parameter and Lambda env var the role could read, and revoke active sessions (rotation does not end issued sessions).
- Delete unused vendor roles or remove Qubole from trust policies.
- Replace `:root` principals with specific vendor principals; add aws:SourceIp / aws:SourceVpce conditions.
- Rotate External IDs and use distinct values per role; least privilege on integration roles.
- Organisation-wide CloudTrail across all accounts and regions, with S3 data events on sensitive buckets.
