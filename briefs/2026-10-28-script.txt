## Deep dive: the camera that called home

Now, the deep dive. And this morning it's about something sitting in the corner of almost every office you've ever walked into.

On Monday, Huntress published research by Harlan Carvey and Lindsey O'Donnell-Welch about a run of incidents across several of its customers in September and October. In each one, the culprit was the same, and it was not a phishing email, not a stolen password, not an exposed firewall. It was the camera management software. The program the facilities team uses to watch the lobby.

Here's how it went.

The program is called simply C M S dot exe, and it lives in a folder called C M S under Program Files. In each case, it launched a second program, called r s dot win thirty two dot exe, from a remote setup folder in the user's application data. It passed that program a remote address, port eight thousand, and a username and password that were both hardcoded as admin. Huntress assesses that second program as a reverse shell. A tunnel out to the attacker, dug from the inside.

The reverse shell then launched a copy of a perfectly legitimate Windows program, the Windows Parental Controls monitor, W p c Mon dot exe. But not from where Windows keeps it. From a copy placed in the user's local application data, in a folder made to look like Microsoft's. Sitting next to it were two D L L files, named after real Windows libraries, I P helper A P I and sam c l i. Windows programs look for their libraries in their own folder first, so the legitimate program loaded the attacker's libraries without a second thought. Those libraries were modified builds of the zlib compression library, with beaconing added. In every incident, the beacon went to the same address, one forty four dot one seventy two dot one sixteen dot thirty seven.

For persistence, a value in the user's Run key in the registry, pointing at the copied parental controls program. So every time someone signed in, the camera software's little passenger woke up and checked in.

That's a well worn sequence. A trusted program, a borrowed Windows binary, a sideloaded library, a registry run key. Nothing in it is new. What's new is the starting point.

So who makes the software? Huntress is careful here, and so am I. The vendor is not confirmed. Strings inside the program point to a C M S package available from a site called k vision dot a i, and to a domain called three r dataware dot com, which Huntress links to a Korean firm called three R Global. Huntress describes that as a possible source, nothing more. There is no attribution to any threat actor. There's also an embedded string, developer slavery, which I'll leave you to interpret. I'd rather not.

And how did the software come to be compromised? Here's the uncomfortable part. Nobody knows, because the application kept no logs. A trojanised installer, a poisoned update channel, or a remote access feature built into the product itself. All possible. None confirmed. It's the sort of software that doesn't log because nobody ever imagined anyone would ask.

Now, why should a consulting firm care about lobby cameras? Three reasons.

First, nobody owns them. Video management software tends to be installed by facilities teams, by the security guard company, or by the building landlord. It runs on a P C at the front desk or in a back office. It's rarely in the I T asset inventory, rarely patched, and often left alone because it works.

Second, it has reach. Camera software needs to talk to cameras across the building, and often to the vendor's cloud. So it usually sits on a network with wide access and outbound connections that nobody questions.

Third, it's a theme. This same week, Ukraine's response team described Russian linked actors hijacking Dahua cameras through the manufacturer's own cloud service, and Dutch intelligence has said Russian state actors use compromised cameras to watch what's happening. The physical security estate is becoming a digital attack surface, and in many offices it's the least defended one.

So, what to hunt. Six things, all in the written brief with the hashes.

One. The process chain itself. C M S dot exe starting r s dot win thirty two, starting W p c Mon.

Two. W p c Mon dot exe running from anywhere other than the Windows System thirty two folder. That alone is a high fidelity signal. The parental controls monitor has no business running from a user's application data.

Three. The I P helper or sam c l i libraries loading from a folder a user can write to.

Four. Run keys in the current user's registry that point into application data.

Five. Outbound connections to that one forty four address, or to port eight thousand from camera or video management hosts.

And six. Any host running camera software from a vendor you can't identify, particularly anything referring to k vision or three r dataware.

And what to do. Inventory video management and C C T V software across the estate, including what's run by facilities, by guard contractors and by landlords in shared buildings. That inventory will probably be the most revealing exercise of the week. If you find the chain, isolate the host, block the address, remove the run key and the files, and then rebuild the machine rather than clean it. Rotate any credentials used on it. Block programs from running out of application data, with Windows' own application control. And put physical security systems on their own network segment, with only the outbound connections they genuinely need.

We spend a great deal of money watching our doors. It's worth spending a little to make sure the thing doing the watching isn't watching us.
